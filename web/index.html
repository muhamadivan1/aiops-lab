AIOps Lab: from raw network alarms to one actionable ticket

A browser-based simulation of an AIOps pipeline for a small telecom network: collect data from three vendors, normalize it into one canonical model, detect anomalies, correlate alarms into incidents, find the root cause, and generate a ticket with a runbook.

By Muhamad Ivan Fadilah Synthetic data, no real network Vanilla JavaScript · no libraries Builds on thesis: Flowbeat canonical data model

Inject faults and tune the detector

Precision and recall are measurable here because the simulator knows exactly where each fault was injected. Lower k catches more faults (recall up) but creates more false alarms (precision down).

01

Collect: three vendors, three formats

Every device reports the same kind of metrics, but each vendor uses different field names, units, and syntax. This is the same problem my thesis solved for medical devices.

02

Normalize: one canonical metric model

Adapters translate each vendor format into the same record: {ts, device, layer, metric, value, unit}. Units are converted (fraction to %, µs to ms, bps to Mbps) so detection can treat every device the same way.

03

Detect: rolling baseline and z-score

For each device and metric, the baseline is the mean and standard deviation of the last 30 normal minutes. A point is anomalous when it is more than k standard deviations away. Anomalous points are excluded from the baseline so a long outage does not become the new normal.

04

Correlate: many alarms, few incidents

Alarms are grouped into one incident when they happen within 10 minutes of each other and the devices sit on the same branch of the topology. The root cause is the most upstream device in the incident that alarmed first. Tap a device to view its chart.

Root causeImpacted (alarming)Normal
05

Act: tickets with runbook and summary

Each incident becomes one ticket with severity, root cause, affected devices, suggested runbook steps, and a short English summary for the NOC team. Here the summary is template-based. In production, an LLM with retrieval over SOPs and past incidents (RAG) could write and enrich it.

Pipeline

COLLECTVendor A JSON, Vendor B key=value text, Vendor C SNMP-style lines
NORMALIZEAdapter per vendor into one canonical record, unit conversion
DETECTRolling 30-minute baseline, z-score, anomaly-free baseline
CORRELATE10-minute window + same topology branch
ROOT CAUSEMost upstream device, earliest alarm
ACTTicket, severity, runbook, summary

Design decisions

  • Adapter + canonical model. Adding a new vendor means writing one adapter, not changing the detector. Same pattern as my thesis Flowbeat, which unified data from two Omron blood pressure monitors.
  • Start with a statistical baseline. A z-score detector is easy to explain to operations teams and gives a benchmark before trying ML models.
  • Topology-aware correlation. A failed aggregation link makes every access node below it alarm. Without topology, the NOC would see many separate problems instead of one.
  • Measure the detector. Precision, recall, alarm compression, and time to detect are shown for every setting, because an AIOps model has to be evaluated, not only built.

Next improvements

  • Seasonality-aware baselines (time of day, day of week) or a forecasting model, so normal peak traffic is not flagged
  • Isolation Forest for multivariate anomalies (CPU, latency, and loss together)
  • Topology loaded from a CMDB or network controller instead of being hardcoded
  • LLM summary with RAG over runbooks and incident history
  • Run on real telemetry from a log and metrics service, and track model drift after deployment

Limitations

All data is synthetic and generated in the browser. The network has 9 devices and 4 metrics. The goal is to understand and explain the AIOps workflow end to end, not to claim production performance.

Pitch 60 detik (bahasa Inggris)

Pakai saat ditanya proyek, saat ditanya cara kamu mempersiapkan diri, atau saat ditanya “do you have anything to add?”. Buka tab Live demo di HP, lalu tunjukkan langkah 01 sampai 05.

To prepare for this role, I built a small AIOps lab to understand the workflow end to end. It simulates a network with three vendors. Each vendor sends data in a different format, so first I normalize everything into one canonical model, the same approach I used in my thesis. Then a rolling z-score detects anomalies, and alarms are correlated by time and topology. For example, one fiber cut produces hundreds of alarm events on four devices, but the system groups them into one incident and points to the aggregation router as the root cause. Finally it creates a ticket with a runbook. I also measure precision and recall, because an AIOps model must be evaluated, not only built. The data is synthetic, but it helped me understand what an AIOps engineer actually does.

Pertanyaan lanjutan yang mungkin muncul

PertanyaanJawaban singkat
Why z-score and not machine learning?It is simple, explainable, and gives a baseline to compare against. Next I would try Isolation Forest or a forecasting model and compare precision and recall.
What happens with daily traffic patterns?A plain rolling baseline can flag normal peaks. I would add seasonality, for example a baseline per hour of day, or use a forecasting model.
How do you know the root cause is correct?Here I can check because I injected the fault. In real operations, I would validate against resolved tickets and ask NOC engineers for feedback.
How would you scale this?Stream data through a message queue, store metrics in a time series database, run detection as a service in containers, and monitor the pipeline itself.
Did you use real data?No, it is synthetic. I built it to learn the workflow, and I am excited to work with real data at Huawei.
